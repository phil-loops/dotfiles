1. What Codex is missing out of the box

The Claude setup here is not vanilla — weeks of conventions live in three places Codex doesn't read automatically:

  • Global instructions — ~/.claude/CLAUDE.md holds the operating rules (forest workflow, comment policy, push policy, dotfiles safety). Codex reads AGENTS.md files instead, and it has none yet.
  • Persistent memory — ~/.claude/projects/-Users-philbrockman-coding-loops/memory/ is a directory of one-fact-per-file markdown notes indexed by MEMORY.md. It records active projects, known bugs, feedback, and hard-won reference facts (e.g. "never parallel count() in ClickHouse"). Codex starts every session amnesiac.
  • The forest metadata convention — stacked branches are described entirely in plain git config (stack-branch.*, stack-project.*, branch descriptions). No tool sets these for you; the agent maintains them by hand as part of every branch operation. Codex doesn't know these keys exist.
  • Session coordination — multiple agent sessions run concurrently on this machine. They avoid collisions via lanes (own + ~/.dotfiles/OWNERS), a patch protocol for contested files, and claude-say for messaging. Codex knows none of this and will happily clobber a live file.

2. Non-negotiable guardrails

Never push to origin. Never open PRs on origin. In the loops repo, origin (Loops-so/loops) is read-only for agents. Push branches and open PRs only on phil-loops (Phil's fork) — and even then, Phil usually does the pushing and PR-opening himself. When in doubt: commit locally, stop, and tell Phil what's ready.
Never amend, never rewrite shared history, never force-push. Always create new commits — PRs are squash-merged so local history doesn't matter. Never add Co-Authored-By lines. A cosmetically wrong commit message on a pushed branch stays wrong; rewriting it clobbers other sessions.
In ~/.dotfiles: never git add -A, never zsource. Phil often has concurrent uncommitted work there. Run git status first, stage explicit paths only, then commit and push. Before editing any dotfiles file, run own who <path> — if another lane owns it (especially ⚠ ACTIVE), author in a throwaway worktree, capture a .patch, and land with git apply --3way.
Comments default to zero. Names and types carry intent. A comment must be (a) preventing a wrong change, (b) unrecoverable from the code, and (c) one line — fail any bar, delete it. Most diffs should add no comments at all; narration ("fetch users", "so that…") is banned.
Heavy typechecks go through the queue. Full typecheck is tsc-turn npx tsc --project tsconfig.node.json --noEmit (that exact command is what CI runs). tsc-turn caps the machine at 2 concurrent heavy compiles — with several agent sessions live, bypassing it flattens the machine. Don't use tsgo in this repo; oxlint/oxfmt are not typecheckers.
The forest viewer (:62333) has mutating endpoints. POST /checkout, /squash, /restack etc. rewrite history or move the main working tree's HEAD. Never probe them with a real branch name; use a nonexistent one (__probe__) and expect 400/404. Never hand-write the gates-green-tree config key — that forges a green CI verdict.

3. The forest workflow (branches as a DAG)

Work ships as a forest of small stacked PRs, not fat branches. The mental model: branches form a DAG; each has one git parent (its rebase base) and optionally requires (fan-in deps it carries as cherry-picks). Every PR merges into main, squash-merged, history always linear — never a merge commit.

The unit of work

  • One branch = one reviewable capability that compiles on its own, named with one verb (add X, emit X, use X in Y).
  • Independent capabilities fork off main as siblings — never chained into a false line just to make the graph linear. Chain only on a real compile/semantic dependency.
  • An integrator that needs several bases records them as requires (fan-in) and carries their commits — metadata over linear history, not merges.
  • The one-dep test: needing exactly ONE other branch's content (compile/build/ runtime) is a chain — set parent = <dep>. requires is reserved for converging two or more independent bases; a single requires on a main-rooted branch is a mis-encoded chain and makes its review diff re-review the dep.
  • Order bottom-up: schema → queries → models → wiring → cleanup. Tests co-locate with the code they test. Prefer 3 × 80-line PRs over 1 × 240-line PR.

The metadata (hand-maintained git config — the viewer only reads it)

# the rebase base (set at creation, update on every reparent)
git config stack-branch.<name>.parent <parent>

# fan-in deps (multivar)
git config --add stack-branch.<name>.requires <dep>

# forest membership (both directions; the project list ROTS on rename/delete — prune by hand)
git config stack-branch.<name>.project <project>
git config --add stack-project.<project>.branch <name>

# one-line purpose, plain language, set THE MOMENT the branch exists — never ask, just do it
git config branch.<name>.description "<what this branch does>"

A freshly created branch with no description is an unfinished operation. Any ancestry change (reparent, rebase-onto, rename) invalidates descriptions — refreshing them is part of the operation, not a follow-up.

Restacking after a merge (raw git, no wrapper)

git fetch origin main && git branch -f main origin/main   # 1. refresh main
# 2. snapshot every member's SHA BEFORE moving anything
# 3. bottom-up: roots onto main, children onto their MOVED parent
git rebase --onto <new-parent> <old-parent-sha> <branch>

After any rebase that empties a branch (diff vs parent is empty / work already in main): contract the graph — delete the branch, rewire its children's parent to the dropped node's parent, migrate all four config keys. Never leave a zero-diff node and never just report "the branch is empty". Squash-merged commits won't match by SHA — use git diff main...branch / git cherry, never rev-list, to decide mergedness. Resolve conflicts in the rebase yourself; a real overlapping-logic conflict means stop and ask Phil.

4. Code standards in the loops repo

  • Layering: queries → models → wiring. Queries are one-DB-call wrappers, no logic, no auth. Models hold business logic with dependency injection. tRPC routers / API routes / job handlers are wiring — they call models, never queries directly. Anything touching multiple tables, conditionals, or auth belongs in models.
  • Files kebab-case (goal-contact-window.ts); query imports as full namespace imports (import * as GoalContactWindowQueries from …, no abbreviations).
  • Inline object-parameter types in signatures — function update(input: { id: string; name?: string }) — no standalone type UpdateInput = … aliases for input shapes.
  • Testing conventions: createX helpers live on query branches (real DB), fakeX on model branches (DI + t.mock.fn()). No pre-emptive helpers.
  • Taskfile over raw commands: task lint, task ci:run, task clickhouse:migrate — run task --list before reinventing.
  • Script runner: one-off scripts go in script-runner/, registered in its index.ts, DRY_RUN=true by default.
  • Restraint: simple over generic, minimal diffs, no churn for purity, migrations carry zero behavior change (offer cleanups as separate branches).

6. Sketches: wiring Codex up to all of this

a. Instructions — port CLAUDE.md into AGENTS.md

Codex merges instruction files top-down: ~/.codex/AGENTS.md (global), then AGENTS.md at each repo root and subdirectory. Sketch:

# global rules (guardrails, dotfiles safety, forest workflow)
cp ~/.claude/CLAUDE.md ~/.codex/AGENTS.md   # then edit: strip Claude-tool specifics

# repo-level rules (layering, Taskfile, typecheck command) → loops repo root AGENTS.md
# (keep it out of origin — either .git/info/exclude it or park it in the fork)

Strip anything that references Claude-only machinery (Skill/agents/artifact tooling); keep every guardrail, the forest sections, and the code standards verbatim.

b. Memory — reuse the existing memory directory read-only

The memory format is plain markdown with frontmatter; nothing about it is Claude-specific. Sketch: add to the global AGENTS.md —

At session start, read
/Users/philbrockman/.claude/projects/-Users-philbrockman-coding-loops/memory/MEMORY.md
and open any linked file relevant to the task. Treat it as background context that may
be stale — verify files/flags it names still exist. If you learn a durable fact, append
a new one-fact file in the same format and add an index line.

Sharing one memory store beats forking it — but if write-contention with Claude sessions becomes an issue, give Codex its own memory-codex/ next door and cross-link.

c. Forest awareness — teach the config schema, not a tool

There is deliberately no wrapper to learn: branch creation, reparenting, restacking are raw git plus the four config keys in §3. The definition-of-done for any branch operation is: parent set, project tagged both directions, description written, and (after ancestry edits) descriptions of every touched branch re-verified. Put that checklist in AGENTS.md verbatim — it's the single highest-leverage paste.

d. Approvals/sandbox — match the trust model

Codex's approval modes map cleanly: workspace-write sandbox with on-request approval approximates how Claude sessions run here. Never grant it network-unrestricted git push; the "never push origin" rule should be enforced by habit and by not approving pushes to origin. Consider a pre-push hook in the loops clone that blocks non-fork remotes as a belt-and-braces backstop.

e. Session coordination — register presence, respect lanes

Codex sessions should follow the same protocol Claude sessions do: claim a lane before dotfiles work (own claim <lane>), check own who before edits, use the worktree→patch→apply --3way protocol for contested files, and message other sessions via claude-say (it targets tmux panes; a Codex pane can receive too). The warm-pool tmux sessions (cw-pool-*) and their worktrees are pre-booted Claude sessions — never treat them as strays or reap them.

f. What "done" means here

  • Change compiles: tsc-turn npx tsc --project tsconfig.node.json --noEmit clean (filter to touched files if the worktree has stale generated tRPC types).
  • Forest config complete (§6c checklist) and descriptions accurate.
  • Committed locally in clean, self-contained commits — not pushed.
  • A short plain-language report to Phil: what's ready, in which worktree, what the merge order is. Phil pushes and opens PRs.
